# ci(release): Release merged PRs one at a time, in merge order

- **Release tag:** `v0.0.36`
- **Source PR:** [#90](https://github.com/mpaulosky/atelier-store/pull/90)

## PR description

### Summary

Part 2 of #86, porting mpaulosky/IssueTracker#172. `release.yml` used a per-PR concurrency group, so two PRs merged close together could reserve versions out of order, and each release opened its own blog PR, which conflicted with the next one.

- **One group:** every run that can release uses `release-main`. A run that can't (an unmerged PR closing, a dispatch from a branch) gets its own group, so it can't replace a pending release run.
- **`plan` job:** `.github/scripts/release_queue.py` lists every merged PR still owed a release, in the order their merge commits sit on `main`'s history. The cutoff is the newest *published* Release, never just the newest git tag. It pages back through closed PRs to the cutoff PR's merge, and fails rather than guess if a listed merge isn't on `main`. Manual runs use the same list, and only a named PR merged into `main` can join it.
- **Serialized release:** a matrix over that list with `max-parallel: 1`. Before tagging, each PR checks that every PR ahead of it has a published Release. Draft Releases count as unreleased. The job publishes a draft for its tag, first appending the release notes (with the `Source PR` line) unless the draft already names the PR.
- **One blog PR per run:** a `docs` job writes every post `main` lacks (via `backfill_blog_posts.py`), rebuilds the tables once, and force-pushes a single `docs/release-notes` branch.
- **Permissions:** workflow-level `permissions: {}`. `plan` is read-only, `release` has `contents: write` and `pull-requests: read`, and `docs` has `contents` and `pull-requests: write`.

This repo's `release.yml` matched IssueTracker's version from before #172, so the new workflow comes over whole. `release_post.py` stays this repo's own (it has fixes IssueTracker lacks); the planner only uses its `GitHub`, `pull`, `releases`, `version_key` and `source_pr_of`. The 8 early Releases that had no blog post were backfilled first in #89, so the `docs` job starts with nothing missing.
