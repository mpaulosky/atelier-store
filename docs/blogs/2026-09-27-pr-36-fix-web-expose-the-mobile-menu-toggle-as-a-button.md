## fix(Web): Expose the mobile menu toggle as a button

- **Release tag:** `v0.0.14`
- **Source PR:** [#36](https://github.com/mpaulosky/atelier-store/pull/36)

### PR description

Fixes #18.

## Problem

The mobile nav drawer's toggle is `<summary aria-label="Menu">`. ARIA in HTML gives `<summary>` no implicit role, so the element reached assistive tech with no role, and the `aria-label` had nothing to name. Before this change, Playwright's snapshot showed the `<details>` as an empty `group`, and `GetByRole(Button, "Menu")` matched nothing.

## Fix

- Adds `role="button"` to the `<summary>` in `SiteHeader.razor`.
- The drawer stays a plain `<details>` element. The header is rendered statically, so this keeps it working without JavaScript or a Blazor circuit, which a `<button>` with `aria-expanded` would have needed.

I checked the result in Chromium's own accessibility tree through the DevTools protocol:

| State | Role | Name | Expanded |
| --- | --- | --- | --- |
| Closed | `button` (focusable) | Menu | `false` |
| Open | `button` (focusable) | Menu | `true` |

Chromium reads the expanded state from `<details>` itself, so no `aria-expanded` attribute is needed. I haven't tested with a real screen reader.

## Tests

- `MobileNavTests` now opens the drawer with `GetByRole(AriaRole.Button, "Menu")`, replacing the `summary[aria-label='Menu']` CSS workaround and its `BUG: #18` comment.
- New bUnit test `SiteHeader_MobileMenuToggle_IsANamedButton` checks the role and label.
- With `role="button"` removed, both tests fail. With it, the solution builds with `-warnaserror` and all bUnit (18) and E2E (11) tests pass. The pre-push check passed.
